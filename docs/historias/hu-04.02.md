# HU-04.02: Conciliação e Edição Manual de Dados Importados

**Ator Principal:** Professor do Departamento / Administrador do Sistema

**Módulo do Sistema:** Módulo de Perfil / Sub-sistema de Ingestão de Dados

**Pré-condição:** O perfil do professor já deve ter sido alvo de pelo menos uma rotina inicial de scraping, ou os campos estruturados de proveniência devem estar inicializados.

---

### 1. Descrição Narrativa

> **Como** professor do departamento de Computação (ou administrador do sistema),
> **Gostaria de** revisar e editar manualmente as informações do meu perfil acadêmico que foram importadas de forma automatizada,
> **Para** corrigir imprecisões textuais, complementar dados omissos das bases externas e validar o estado final do meu currículo público na plataforma.

---

### 2. Checklist de Componentes da Interface (UI/UX)

*O que a tela de edição de perfil do docente precisa conter visualmente:*

* [ ] Campos de entrada de texto editáveis para: `Linhas de Pesquisa`, `Titulação`, `Habilidades` e `Links de Produção Acadêmica`.
* [ ] Badges visuais de proveniência ao lado de cada campo (ex: ícone do Lattes, ícone do SIGAA ou tag `[Editado Manualmente]`).
* [ ] Campo oculto (Hidden Input) no formulário contendo a versão atual do documento: `version_id` (ou timestamp de mutação).
* [ ] Botões de ação explícitos: `Salvar Alterações` e `Descartar Edições`.
* [ ] **Modal de Resolução de Conflitos:** Tela acionada em caso de erro de concorrência, exibindo lado a lado: "O que você digitou" vs. "O que o sistema atualizou via Scraping", com botões para `Forçar Minha Versão` ou `Atualizar com os Dados do Servidor`.

---

### 3. Critérios de Aceitação (Regras de Negócio e Validações)

*O comportamento esperado do sistema e suas restrições lógicas:*

#### Fluxo Principal (Sucesso):

* **Cenário 1: Edição Manual sem Conflitos Concorrentes**
* **Dado** que o professor abriu a tela de edição de perfil (carregando a versão do documento como $v_1$),
* **Quando** ele modificar o campo "Linhas de Pesquisa" e clicar em "Salvar Alterações",
* **Então** o sistema deve verificar no banco se a versão atual ainda é $v_1$, persistir os dados novos, alterar o metadado de proveniência daquele campo específico para `manual` (atendendo ao **RF14**), incrementar a versão para $v_2$ ($v_{atual} = v_{anterior} + 1$) de forma atômica e fechar a edição.



#### Fluxo de Exceção (Validações e Tratamento de Erros):

* **Cenário 2: Violação de Concorrência por Scraping Simultâneo (RF19)**
* **Dado** que o professor abriu a tela de edição (carregando a versão $v_1$),
* **Quando** ele tentar salvar suas alterações, mas a rotina de manutenção/scraping tiver alterado o documento no banco de dados frações de segundo antes (incrementando a versão no banco para $v_2$),
* **Então** a API deve recusar a escrita do professor, disparar uma exceção de concorrência, impedir a perda cega de dados e retornar o código HTTP 409 (Conflict), abrindo o Modal de Resolução de Conflitos na interface.


* **Cenário 3: Tentativa de Remoção de Identificadores Único Estritos (RF20)**
* **Dado** que o professor ou administrador está limpando campos do formulário,
* **Quando** ele tentar salvar o perfil removendo ou deixando em branco o ID do Lattes ou o ID do SIGAA,
* **Então** o sistema deve bloquear a ação com erro inline: *"Os identificadores de fontes externas são obrigatórios para a manutenção do perfil e não podem ser removidos."*



---

### 4. Impacto Estrutural e Arquitetura de Dados

*Mapeamento lógico de persistência e controle de estado matemático:*

* **Coleções/Entidades Afetadas:** `professores_perfis`
* **Atributos Modificados/Atualizados:**
* `version`: inteiro incremental incremental genérico usado para o controle do algoritmo otimista ($\Delta = +1$).
* `metadata_provenance.[campo]`: string que transiciona de `"importado_lattes"` para `"manual"`.
* `updated_at`: timestamp do sistema atualizado no momento exato do commit.
